01

What you are replacing

The app has exactly one seam:

// data/engine/GaitAnalyzer.kt
interface GaitAnalyzer {
    val engineName: String
    val isMock: Boolean
    fun analyze(input: SessionInput): Flow<AnalysisProgress>
}

Two implementations sit behind it. MockGaitAnalyzer fabricates a report; RemoteGaitAnalyzer is a stub carrying this contract in its KDoc. To switch: 

// di/AppModule.kt
fun gaitAnalyzer(context: Context): GaitAnalyzer =
    RemoteGaitAnalyzer(baseUrl = "https://…")     // was MockGaitAnalyzer { … }

Leave isMock true until scores are real

Setting isMock = false removes the “DEMO — mock inference” banner. Keep it true through integration testing: that banner is the only thing stopping a screenshot of synthetic output being taken for a clinical result.

02

The input you receive

Two short clips per assessment, uploaded together.

sagittal
22 scores

Lateral camera, side-on to the walkway. 11 items × 2 limbs.

coronal
12 scores

Walkway-end camera, facing the child. 6 items × 2 limbs.

This mirrors the CGV capture protocol: a primary camera at the terminus of an 8 m walkway for the coronal view, and a secondary camera oriented orthogonally, facing the middle of the walkway, for the sagittal view. Both run simultaneously. Clips are typically 3–5 seconds — one walk past the camera.

The plane is declared, not inferred

The app presents two labeled slots and will not submit until both are filled. Do not try to detect which clip is which — you are being told, and the assignment is authoritative.

Clips come from the device photo picker, so expect H.264/HEVC MP4, 480p to 4K, 24–60 fps, arbitrary rotation metadata, and occasionally a clip where the child leaves frame.

03

The endpoint

Both clips are short, so this is a single round trip — no event stream, no job polling. Exactly two multipart parts, named sagittal and coronal. 

POST {baseUrl}/v1/assessments
Content-Type: multipart/form-data

Success — 200

{
  "patternSummary": "Findings consistent with right spastic hemiplegia — unilateral
                      right-sided deviation with a compensating left limb.",
  "clipQuality": { "SAGITTAL": 0.88, "CORONAL": 0.81 },
  "scores": [
    { "item": "IC", "limb": "L", "label": "TYPICAL",  "confidence": 0.85 },
    { "item": "IC", "limb": "R", "label": "ATYPICAL", "confidence": 0.89 }
  ]
}

A complete valid response — all 34 entries — is checked in at docs/example-response.json. Use it as a fixture.

FieldTypeNotes
patternSummarystringOne sentence, shown verbatim on the summary card. Under ~200 chars. Wording matters — see §06.
clipQualityobjectSAGITTAL and CORONAL, each 0..1. How usable the clip was: framing, occlusion, whether the child stayed in shot. Your channel for “this clip was poor”.
scoresarrayExactly 34 entries — 17 items × 2 limbs.
scores[].itemstringEVGS code from the table in §04.
scores[].limbstring"L" or "R".
scores[].labelstring"TYPICAL" or "ATYPICAL".
scores[].confidencenumber0..1. Not 0..100.
scores[].viewstringOptional. If present must equal the item's plane; the app derives the plane from the item and ignores a contradictory value. Useful as a self-check.

Failure — 4xx / 5xx

{ "error": "Sagittal clip contains no detectable person." }

The message is shown to the user in a snackbar, so write it for a clinician, not a log file.

The item table and the plane split

This is the part most likely to be got wrong, and it fails silently when it is. Each item is observable from exactly one plane.

Flexion and extension arcs, foot clearance, forward trunk lean.

Score each item from the clip whose plane can actually see it. A lateral view cannot resolve hind-foot varus or pelvic obliquity; a frontal view cannot resolve knee flexion arc or forward trunk lean. Scoring KEX off the coronal clip will produce a number, and that number will be meaningless — this split is the entire reason the app takes two clips instead of one.

The app surfaces provenance in the UI (“Scored from: Coronal clip”), so a clinician reviewing a finding sees which camera it came from. Getting this wrong is visible to them, not only to you.

Binary, not ordinal

EVGS is natively a three-point scale — 0 normal, 1 moderate deviation, 2 marked deviation. The paper binarises it by merging 1 and 2, because score 2 is too rare in the cohort to learn from, and the app follows suit. So TYPICAL = 0 and ATYPICAL = 1 or 2.

If your model produces the full ordinal scale, keep it internally and collapse at the API boundary — but tell us, because surfacing severity is an obvious next step for the UI and we would rather not re-derive it later.

Full clinical definitions and the native 0/1/2 criteria for every item live in data/model/Evgs.kt, transcribed from Appendix B of the paper. That is the reference the app shows users; keep your scoring aligned to it.

05

Validate before you integrate

A response that violates the contract does not crash the app — it renders a report that is quietly wrong, which is worse. So there is a validator. 

./tools/validate-response.py your-response.json
curl -s -F sagittal=@a.mp4 -F coronal=@b.mp4 $BASE/v1/assessments | ./tools/validate-response.py -

It checks all 34 present, no duplicates, the 22/12 plane split, valid codes, valid ranges, and view consistency — plus soft warnings for the mistakes that look plausible, like constant confidences or 0..100 sent as 0..1. 

$ ./tools/validate-response.py docs/example-response.json
VALID — 34 scores, plane split correct, 0 warning(s)

Wire it into your CI.

06

Wording of patternSummary

This string appears on the summary card directly under the flagged-item count. It is the one piece of free text you control, and it is read by clinicians.

The mock's convention is "Findings consistent with <pattern> — <clause>." Note what it deliberately does not do:

  • It does not name a diagnosis. “Findings consistent with a bilateral equinus pattern” — not “the child has cerebral palsy”.
  • It does not recommend action.
  • It hedges by construction. A screening tool at ~85% per-item accuracy has not diagnosed anything.

If your model has a classification head over conditions, phrase the summary from the observed kinematics rather than the class label. This is a screening aid for a pediatrician, not a report.

Two caveats before treating 84% as the bar

The test split is small. Per-item accuracies are quantised on denominators of roughly 26–28 videos, so a single sample moves a number by about 4 points and the 95% confidence interval on 84% is around ±13.

The paper's significance test pools McNemar over the 34 items rather than over samples, which overstates significance given left/right and shared-video dependence.

Treat 84% as the right order of magnitude, and build a larger held-out split.

The app displays confidences drawn around these published per-item values, so if your calibration differs markedly the numbers on screen will stop matching the paper. That is fine — just expected.

Method, for reference

The paper's winning configuration is a VideoMAE v2 encoder pre-trained on Kinetics-710 and fine-tuned on CGV with two additions: token-level kinematic prompting, rendering the skeleton onto the RGB frame so patches carrying joints become implicit kinematic tokens; and mask-guided patch pruning, keeping only patches with sufficient foreground mask, deterministically, instead of MAE-style random masking.

Ablation: prompting +3, pruning +9, both +15 over the VideoMAE v2 baseline. Random masking hurts. Input is 16 frames at 30 fps; 32 frames gained a further ~3.7 points at quadratic cost.

08

Consent and data handling

Read before your first request

The app currently has no network code at all. That is why the import screen says “Clips stay on this device. Nothing is uploaded.” The moment RemoteGaitAnalyzer goes live, pediatric clinical video starts leaving the device and that statement becomes false.

Before you ship:

  1. The UI copy must change. ImportScreen.kt and the README both make the no-upload claim.
  2. Consent is separate from the code. The CGV dataset was collected under IRB approval 202106202 as a retrospective study. Live upload from a clinic is a different activity and needs its own review.
  3. De-identification. The dataset pipeline mosaics faces (RetinaFace + SAM 3) with manual verification of every output. Clips arriving from a phone are not de-identified. Decide whether that happens on device before upload or server-side on receipt — and if server-side, raw video exists on your infrastructure and that has to be justified.
  4. Retention. Decide whether clips are kept after scoring. The dataset licence (CC BY-NC 4.0) forbids using this video as foundation-model training material without separate authorisation; clips uploaded from clinics are not covered by it at all.
  5. Transport. TLS, obviously. Also no identifiers in URLs or logs, and consider whether a sessionId should be derivable from anything.

None of this is the app's problem to solve, which is exactly why it is on this list — it will otherwise fall between the two teams.

Running the app to test against

source env.sh
./gradlew assembleDebug

To exercise the flow without a phone:

sdkmanager --sdk_root="$ANDROID_HOME" emulator "system-images;android-35;google_apis;arm64-v8a"
./run-emulator.sh --headless
./tools/make-test-video.sh 4 --push     # generates and pushes both synthetic clips

tools/dev-loop.sh rebuilds, reinstalls and screenshots on every save in about two seconds — the fastest way to see your responses rendered. tools/uidrive.py drives the UI by on-screen label if you want to script it.

The synthetic clips are stick figures: fine for exercising the report, useless as model input. Use real footage for anything involving pose.

10

Open questions for you

Positions the app has taken that you may want to revisit.

  1. Q1 Ordinal vs binaryWe collapse to typical/atypical because the paper does. If your model gives 0/1/2 reliably, say so and we will surface severity.
  2. Q2 Per-clip confidenceclipQuality is one number per clip. If you can report why a clip scored poorly — child left frame, occlusion, too few gait cycles — that is more actionable and we would show it.
  3. Q3 Latency budgetThe mock takes 3–7 s deliberately. If real inference takes 30 s or more we should move to a job-and-poll model rather than a blocking request. Tell us early; it changes the progress UI.
  4. Q4 Which items your model is weakest onThe paper's worst are WAD (70% left) and SAD (74% right). If certain items are unreliable, returning them with a low confidence beats returning them confidently — the UI already renders confidence per item.
  5. Q5 Single-clip fallbackBoth clips are currently required. If a clinician only has one, we could score that plane and mark the other 6 or 11 items unobserved. Worth doing?
